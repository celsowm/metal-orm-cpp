# Remote cache adapters

MetalORM C++ 0.0.37 adds first-party remote-cache semantics without making a Redis client library a mandatory ORM dependency.

The cache core continues to depend on the small `CacheProvider` capability surface. Remote transports are injected behind backend interfaces:

```text
QueryCacheManager
        |
        v
CacheProvider
   |                 |
   v                 v
KeyValueCacheAdapter RedisCacheAdapter
   |                 |
   v                 v
KeyValueBackend      RedisBackend
   |                 |
   +------ application/client integration ------+
              hiredis / redis-plus-plus /
              Boost.Redis / custom service / etc.
```

This keeps dependency direction pointed toward MetalORM abstractions rather than a specific networking library.

## Portable `QueryResult` codec

Remote stores usually expose strings or byte buffers rather than C++ objects. MetalORM therefore ships a versioned binary codec:

```cpp
auto payload = metal::encode_query_result(result);
auto restored = metal::decode_query_result(payload);
```

The current payload magic is `MORMC001`.

The codec preserves every current `metal::Value` alternative:

- SQL `NULL`;
- `std::int64_t`;
- `double`;
- `std::string`, including embedded NUL bytes;
- `bool`;
- `metal::Blob` with arbitrary octets.

It also preserves `QueryResult::affected_rows` and `last_insert_id`.

Row fields are serialized in sorted column-name order so equivalent rows produce deterministic payloads even though `Row` is an `unordered_map`.

Malformed, truncated, unsupported-version and duplicate-column payloads are rejected by `CacheCodecError`. Remote adapters treat such a payload as a cache miss and attempt best-effort eviction, preventing stale cache bytes from breaking the underlying database query after an application upgrade.

The codec is deliberately not JSON-based. Cache transport does not introduce a JSON dependency into the ORM core, and binary BLOB values do not need base64 expansion internally.

## Generic key/value adapter

`KeyValueCacheAdapter` is the C++ equivalent of the TypeScript `KeyvCacheAdapter` pattern.

Implement the minimal backend:

```cpp
class MyStore final :
    public metal::KeyValueBackend,
    public metal::KeyValuePrefixBackend {
public:
    std::optional<std::string> get(std::string_view key) override;

    void set(
        std::string key,
        std::string value,
        std::optional<std::chrono::milliseconds> ttl) override;

    void delete_key(std::string_view key) override;

    std::vector<std::string> keys_with_prefix(
        std::string_view prefix) override;
};
```

Then:

```cpp
auto backend = std::make_shared<MyStore>();
auto cache = std::make_shared<metal::KeyValueCacheAdapter>(backend);

metal::QueryCacheManager manager{cache};
```

Capabilities are derived from the actual backend:

- TTL: supported by `KeyValueBackend::set`;
- prefix invalidation: supported only when the backend also implements `KeyValuePrefixBackend`;
- tags: deliberately unsupported.

Calling `invalidate_tags()` on this adapter throws an explicit capability error. Use `RedisCacheAdapter` or another tag-capable provider when tags are required.

This is slightly stricter than the current TypeScript Keyv adapter, whose static `capabilities.prefix` says `true` even though `invalidatePrefix()` can fail when the selected Keyv store has no iterator. C++ reports the real runtime capability instead of reproducing that false positive.

## Redis adapter

`RedisCacheAdapter` implements the full remote feature set used by the TypeScript Redis adapter:

- TTL delegated to the backend's native expiration support;
- tag membership through Redis-style sets;
- prefix invalidation through backend key scanning;
- batched deletion through `RedisBackend::delete_keys()`;
- tenant-aware keys remain generated by the existing `CacheStrategy`.

A backend implements:

```cpp
class MyRedisBackend final : public metal::RedisBackend {
public:
    // KeyValueBackend
    std::optional<std::string> get(std::string_view key) override;
    void set(
        std::string key,
        std::string value,
        std::optional<std::chrono::milliseconds> ttl) override;
    void delete_key(std::string_view key) override;

    // KeyValuePrefixBackend
    std::vector<std::string> keys_with_prefix(
        std::string_view prefix) override;

    // Redis set capabilities
    void add_set_members(
        std::string_view key,
        const std::vector<std::string>& members) override;
    std::vector<std::string> set_members(
        std::string_view key) override;

    // Optional optimization
    void delete_keys(const std::vector<std::string>& keys) override;
};
```

For a real Redis implementation, `keys_with_prefix()` should normally use cursor-based `SCAN` rather than blocking `KEYS`, matching the TypeScript adapter's production strategy.

Configure the adapter:

```cpp
auto redis_backend = std::make_shared<MyRedisBackend>();

auto cache = std::make_shared<metal::RedisCacheAdapter>(
    redis_backend,
    metal::RedisCacheAdapterOptions{
        .tag_prefix = "metal:tag:",
        .dispose_backend = false
    });

metal::QueryCacheManager manager{cache};
```

`RedisCacheAdapter::capabilities()` reports tags, prefix invalidation and TTL as supported.

## Tags

The existing `QueryCacheManager` already registers tags through the segregated `CacheTagRegistrar` capability.

For example, with a tenant-aware cache key:

```text
tenant:7:dashboard
```

and tags:

```text
users
dashboard
```

`RedisCacheAdapter` adds the key to sets such as:

```text
metal:tag:users
metal:tag:dashboard
```

Invalidating `users` reads the set members, deletes the tag set, deduplicates the referenced cache keys and removes those cache entries.

## TTL behavior

A positive `std::chrono::milliseconds` TTL is passed to the backend.

A zero TTL is normalized to no-expiration, matching the existing memory adapter and the TypeScript Redis adapter's falsy-zero behavior.

Negative TTL values are not silently rewritten; a concrete backend may use them for immediate expiration or reject them according to its own native contract. Normal `QueryCacheManager` durations are already validated as non-negative.

## Backend ownership

Injected backends belong to the application by default:

```cpp
.dispose_backend = false
```

Calling `QueryCacheManager::dispose()` therefore does not unexpectedly close a shared Redis connection or connection pool.

When the adapter is meant to own that backend instance, opt in explicitly:

```cpp
metal::RedisCacheAdapterOptions{
    .dispose_backend = true
}
```

The same ownership option exists for `KeyValueCacheAdapter`.

This corresponds to the TypeScript Redis adapter distinction between an externally supplied ioredis instance and a connection created by the adapter itself.

## What remains external

MetalORM now owns the **cache semantics and adapter policy**, but intentionally does not own a specific network stack.

A concrete hiredis/redis-plus-plus/Boost.Redis bridge can live in an application, integration package, or future optional MetalORM package. The ORM core remains buildable without Redis development libraries.

That boundary is intentional: changing Redis client libraries should not require changing `QueryCacheManager`, query ASTs, sessions, DTOs or ORM persistence code.
